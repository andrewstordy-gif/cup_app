# R1-068 — Cup reuse after local tasting completion

19 October 2026. Status: recorded and deferred to the physical NFC consistency/reassignment stage; implementation not started. Product Owner asks to save this issue and address it alongside related creator/participant work. PM `/root`; author and independent reviewers to be assigned before implementation. Risk HIGH for later physical writes, recovery and historical data preservation.

## Report and diagnosis

On the R1-067 phone candidate, the user completed a CVA session named Test, shown COMPLETE, then tried to assign the same physical cup to a new Legacy session named Test 2. Assignment failed with “Cup already in use” and an assertion that the earlier session was active. Screenshots: `/Users/andrewstordy/Downloads/Screenshot 2026-10-19 at 08.30.13.png` and `/Users/andrewstordy/Downloads/Screenshot 2026-10-19 at 08.33.48.png`. No phone database inspection or physical reproduction has been performed by an agent.

Source-backed likely cause: `CuppingSessionDetailsScreen.js` calls `findPendingSessionByCupUUID`, whose SQL checks raw `sessions.status IN ('new','pending','in_progress')`. Local completion instead qualifies a revision in `completeLocalTasting`; the presentation can project COMPLETE without changing that older status field. Thus the assignment guard can disagree with the screen. The error banner additionally suggests finishing the old session even when the user already completed it. Confirm the selected conflict row and identifier normalization in an isolated reproduction; do not assume the screenshots identify every local assignment to that cup.

## Authority and intended scope

PRODUCT_SPEC6.7/6.8, FR-020/028A, NDEF_PROTOCOL and RELEASE_1_ARCHITECTURE_DATA_CONTRACT govern reuse. Local tasting completion is not host-global closure and does not clear physical metadata. Preserve old CVA scores, notes, pins, provenance and completion; never delete or reopen a historical tasting merely to free hardware. A physical cup may be reused, but the previous physical assignment must be cleared and separately verified before a new assignment is written and verified. An active local conflict must not be bypassed merely because some unrelated participant completed their tasting.

Address this with implementation-plan stage4: review exact unassignment bytes and affected cup-count/position metadata; durably stage clear/reassignment intent before writing; separate physical read-back verification; restart/resume at verification; guard failures and stale callbacks. Keep participant local sample removal and whole-session deletion separate: neither changes a cup. Do not fix by only dropping the conflict check, silently overwriting NFC, globally closing the old session, or making physical clearing depend on deleting saved results. Existing post-completion setup locks must not be broadly removed to provide reuse.

Expected audit paths: `src/data/sessionRepository.js` conflict lookup and trusted state/pin/ownership boundaries; `src/features/cupping/screens/CuppingSessionDetailsScreen.js` assignment flow; `src/features/cupping/constants/sessionDetails.js` conflict/error metadata; `src/features/cupping/components/AddCoffeeSampleSheet.js` warning; `src/services/nfcServiceMinimal.js` normalization and physical write/verify; future durable operation storage only after reviewed schema/protocol design. This list is an audit boundary, not permission to implement or invent clearing bytes now. No form/scoring/Legacy calculation changes.
