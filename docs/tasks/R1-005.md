## Acceptance criteria

- A new locally generated standalone record/profile ID is a lowercase, cryptographically random 128-bit UUID. No timestamp or `Math.random()` fallback can produce an identity or access-related reference. The current prototype's session-row alias to the 14-character reference is explicitly retained until the production-schema task.
- A new NDEF/session reference remains exactly 14 lowercase ASCII alphanumeric characters, uses cryptographically secure random bytes without modulo bias, and never emits the `NO-SESSION` sentinel.
- Generation works without an internet connection on a rebuilt iPhone development build containing `expo-crypto`. Use its documented secure `getRandomValues` or `randomUUID`; do not use `getRandomBytes`, whose SDK 54 documentation permits a development-mode `Math.random` fallback. If the secure random source is unavailable, creation fails safely and visibly before a new session, record, or tag write is reported successful.
- Existing saved session references and IDs remain readable and unchanged. This task does not import or mutate prototype data as a migration.
- Collisions in new local creation do not overwrite an existing record; the caller retries with a new secure reference or reports a visible failure. Existing unique database constraints remain effective.
- Focused tests cover output shape, secure-source failure, collision handling, and preservation of the current session/NFC reference format. Existing relevant NFC checks pass.
- No unrelated user-facing UI or NFC payload behaviour changes. Expo Crypto is the only approved new native dependency; any further dependency or configuration need returns to the PM.
- The implementation handoff distinguishes automated checks from physical device verification and records the exact commit tested.

## Decisions

- The PM selected secure identifier generation as the first bounded Release 1 implementation prerequisite because the current persistence path already survives app restart but contains insecure random fallbacks.
- This task improves current generation paths without representing the prototype SQLite store as the compliant encrypted Release 1 production database. The distinct production store and event/revision transaction are later tasks.
- No existing prototype records are deleted or migrated. Andrew previously approved that prototype data need not be retained for Release 1 cutover, but this task performs no cutover.
- The PM approved adding the SDK-matched native `expo-crypto` dependency after implementation inspection showed no explicit secure RNG package/polyfill in the repository. The agent must record the resolved version and native rebuild evidence; the currently installed development binary cannot be assumed to contain the new native module.
- The prototype currently aliases its 14-character session reference as the `sessions.id` row key. R1-005 secures that reference and creates UUIDs for standalone record/profile IDs but does not split the legacy session row into a distinct domain UUID. The production-schema task will implement that separation; this task must not claim full section 4.1 domain-model conformance.
